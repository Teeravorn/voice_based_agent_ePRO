# voice_based_agent_ePRO

POC สำหรับวิทยานิพนธ์ **Conversational Agent for PROM** — ระบบที่คุยกับผู้ป่วยด้วยเสียง
เพื่อเก็บแบบประเมินผลการรักษา (ePRO) แทนที่จะให้พยาบาลนั่งถามทีละข้อ

POC นี้ยังไม่ใช่ตัวระบบเต็ม แต่ตัดมาเฉพาะ **สองชิ้นที่เสี่ยงที่สุด** เพื่อพิสูจน์ว่าแนวทางนี้ไปต่อได้

```
ไฟล์เสียงคำตอบผู้ป่วย
        │
        ▼
  ASR (typhoon-whisper-turbo)          ← รันบนเครื่อง
        │  ข้อความภาษาไทย
        ▼
  Option Extractor (qwen3:4b ผ่าน Ollama)   ← รันบนเครื่อง
        │  JSON ที่บังคับรูปแบบด้วย schema
        ▼
  คะแนน QuickDASH 1-5 + เหตุผล + ความมั่นใจ
```

ชิ้นที่ยากที่สุดคือ **option extractor** เพราะผู้ป่วยไม่ได้ตอบว่า "สาม" แต่ตอบว่า
"ก็พอได้อยู่ แต่ไม่เหมือนเมื่อก่อน" ระบบต้องแปลงคำพูดแบบนั้นให้เป็นคะแนนที่ใกล้เคียง
กับที่พยาบาลจะให้

### สิ่งที่ยังไม่มีใน POC นี้

dialogue manager / state machine, TTS และเสียงคำถามที่ pre-render ไว้, ภาพประกอบ,
การคิดคะแนนรวมของ DASH, WangchanBERTa และการเก็บข้อมูลจากผู้ป่วยจริง

## วิธีรัน

### โหมด text — ตรวจ extractor อย่างเดียว (ไม่ต้องมีไฟล์เสียง)

```bash
python main.py --mode text
```

ป้อนประโยคต้นฉบับจาก `evaluation/manifest.csv` เข้า extractor ตรง ๆ ผลที่ได้คือ
**เพดานความแม่นของ extractor** ใช้ตอนปรับ prompt เพราะรันเร็วและไม่ต้องใช้ ASR

### โหมด asr — ทั้ง pipeline (ต้องมีไฟล์เสียงแล้ว)

```bash
python main.py --mode both
```

ถอดเสียงจริงก่อนแล้วค่อยเข้า extractor **ส่วนต่างระหว่างสองโหมดคือต้นทุนที่ ASR เพิ่มเข้ามา**
ซึ่งเป็นตัวเลขที่ต้องรายงานเป็น limitation ในเล่ม

### ตัวเลือกอื่น

```bash
python main.py --mode text --model qwen3:8b     # เทียบโมเดล
python main.py --engine systemone --mode asr    # ใช้ OpenThai-SystemOne แทน qwen
python main.py --think off                      # ปิด reasoning ของ qwen (เร็วกว่า 12 เท่า)
python main.py --only q9 --only q11             # รันเฉพาะบางข้อ
python main.py --mode text --limit 5            # รันแค่ 5 แถวแรก
```

### ความเร็วที่วัดได้

วัดบนคำตอบ 15 อันชุดเดียวกัน แยกกระบวนการละ engine (ASR อยู่ร่วมใน VRAM ด้วย
ซึ่งตรงกับการใช้งานจริง) บน RTX 4060 8 GB

| engine | mean | median | p95 | max | exact match |
|---|---|---|---|---|---|
| qwen3:4b `--think on` | 24,542 ms | 21,179 | 40,096 | 42,686 | 84.6% |
| qwen3:4b `--think off` | 2,049 ms | 1,813 | 2,779 | 4,393 | 84.6% |
| OpenThai-SystemOne | **442 ms** | 437 | 475 | 523 | 76.9% |

ASR ~520–570 ms ทุกกรณี ความแม่นของ qwen เท่ากันทั้งเปิดและปิด reasoning
ดังนั้น `--think on` คือการจ่ายเวลาเพิ่ม 12 เท่าโดยไม่ได้อะไรกลับมา

ผลดิบทุกครั้งถูกเก็บเป็น JSON ใน `evaluation/results/` (มี prompt, transcript และคำตอบดิบ
ของโมเดลครบ เอาไปใส่ appendix หรือวิเคราะห์ย้อนหลังได้)

## การอัดไฟล์เสียง

`evaluation/manifest.csv` มีสคริปต์คำตอบ 15 อันเตรียมไว้แล้ว อัดเสียงตามคอลัมน์ `script_th`
แล้วบันทึกเป็นไฟล์ตามชื่อในคอลัมน์ `audio` ลงในโฟลเดอร์ `evaluation/answers/`

รูปแบบไฟล์: wav อะไรก็ได้ที่ ffmpeg อ่านออก (จะถูก resample เป็น 16 kHz ให้เอง)
ยังอัดไม่ครบก็รันได้ ไฟล์ที่ยังไม่มีจะถูกข้ามพร้อมแจ้งเตือน

คำตอบ 15 อันแบ่งเป็น 4 ประเภท เพื่อให้เห็นว่าระบบพังตรงไหน

| ประเภท | จำนวน | ตัวอย่าง | ใช้วัดอะไร |
|---|---|---|---|
| `direct` | 3 | "ไม่ยากเลยค่ะ เปิดได้ปกติ" | พูดตรงตัวเลือก ควรได้ 100% |
| `natural` | 7 | "ต้องให้ลูกเปิดให้ทุกครั้งเลยค่ะ" | เล่าอาการแบบที่ผู้ป่วยพูดจริง — เป้าหมายหลัก |
| `ambiguous` | 3 | "ก็พอได้อยู่ค่ะ แต่ไม่เหมือนเมื่อก่อน" | โมเดลยอมตัดสินใจไหม หรือหนีไปตอบ 0 |
| `meta` | 2 | "เมื่อกี้ถามว่าอะไรนะคะ" | แยกออกไหมว่าผู้ป่วยไม่ได้กำลังตอบคำถาม |

คอลัมน์ `gold_value` รองรับเฉลยหลายค่าเช่น `2|3` สำหรับคำตอบที่กำกวมจริง ๆ ซึ่งพยาบาลสองคน
ก็อาจให้คะแนนต่างกัน การบังคับให้มีเฉลยเดียวในเคสแบบนี้จะทำให้ตัวเลขความแม่นต่ำกว่าความจริง

## ตัวชี้วัด

| ตัวชี้วัด | ความหมาย |
|---|---|
| exact match | ตรงเฉลยเป๊ะ — ตัวเลขหลักที่จะเอาไปเทียบกับพยาบาล |
| ±1 agreement | พลาดไม่เกินหนึ่งระดับ บอกว่าเข้าใจ "ทิศทาง" ของอาการถูกไหม |
| undecided rate | ตอบ 0 ทั้งที่ควรให้คะแนนได้ — failure mode ที่เจ็บที่สุด เพราะต้องให้พยาบาลมาถามซ้ำ |
| meta-intent accuracy | แยกออกไหมว่าผู้ป่วยขอให้ทวนคำถาม / ไม่รู้คำตอบ |

ยังไม่คำนวณ quadratic weighted kappa เพราะ n = 15 ไม่มีความหมายทางสถิติ เก็บไว้ตอนเทียบกับ
พยาบาลจริง ซึ่งเป็นตัวชี้วัดหลักของงาน (ไฟล์ผลลัพธ์เก็บข้อมูลดิบครบพอให้คิดย้อนหลังได้)

### จุดที่แก้แล้วความแม่นเปลี่ยนทันที

`extractor/prompt.py` — ลำดับ field ใน JSON schema **มีผลต่อความแม่นโดยตรง**
เพราะ structured output ใช้ constrained decoding คือบังคับให้โมเดลสร้าง token
ตามลำดับที่ประกาศไว้ ลำดับ field จึงเท่ากับลำดับความคิดของโมเดล

1. `reason` ต้องมาก่อน `value` — ถ้าสลับกัน โมเดลต้องฟันธงคะแนนเป็น token แรกโดยยังไม่ได้
   ประมวลผลอะไรเลย
2. `reason` ต้องมี `minLength` — ถ้าปล่อยให้เป็น `""` ได้ decoder จะปิดสตริงทันที
   เพราะเป็นทางที่สั้นที่สุดที่ยัง valid แล้วก็ไม่เหลืออะไรให้ยึดตอนเลือก `value`

รันโหมด text วัดก่อนและหลังเสมอเมื่อแก้ไฟล์นี้

### `think=False` มีความหมายต่างกันสองแบบ

`engine/chat.py` — พารามิเตอร์ `think` ของ Ollama ทำงานคนละอย่างขึ้นกับว่าส่ง `format` ไปด้วยไหม

**มี `format=schema`** (คือ `chat_json()` ที่ pipeline ใช้จริง) — `think=False` ปิด reasoning ได้จริง
เพราะ grammar บังคับให้ token แรกต้องเป็น `{` โมเดลจึงเปิดบล็อก `<think>` ไม่ได้ตั้งแต่แรก
วัดกับ qwen3:4b คำถามเดียวกัน ได้ `value` เท่ากันทั้งสองแบบ แต่

| | เวลา | token |
|---|---|---|
| `think=False` | 2.8 วินาที | 156 |
| ไม่ใส่ / `think=True` | 23–27 วินาที | ~1,300 |

**ไม่มี `format`** (คือ `chat()` ที่ใช้ตอน debug) — `think=False` **ไม่ได้** สั่งให้โมเดลหยุดคิด
มันสั่งแค่ว่า "ไม่ต้องแยก reasoning ออกมาเป็นช่อง `thinking`" ผลคือ reasoning ไหลลงไปปนใน
`message.content` ทั้งก้อน ตรงนี้จึงต้องไม่ส่ง `think` เลยเมื่อค่าเป็น `False`
(ต่อท้าย prompt ด้วย `/no_think` ไม่ช่วย ลองแล้วโมเดลยังคิดเท่าเดิม)

## ข้อจำกัดที่รู้อยู่แล้ว

- **ASR** ใช้ของสำเร็จรูป ไม่ได้ fine-tune กับเสียงผู้ป่วย นับเป็น limitation ของงานตามที่ตั้งไว้
- **VRAM** เครื่องที่ทดสอบเป็น RTX 4060 (8 GB) qwen3:4b กินราว 3.2 GB เมื่อรวมกับ Whisper
  แล้วเหลือ headroom ไม่มาก ถ้าจะใช้ qwen3:8b (5.2 GB) พร้อม ASR อาจต้องสลับกันโหลด
- **n = 15** ยังเป็นแค่การทดสอบความเป็นไปได้ ไม่ใช่การประเมินผลจริง
- คำตอบที่กำกวมบางอันไม่มีเฉลยที่ถูกต้องเพียงคำตอบเดียว เช่น "ปวดจนต้องกินยาแก้ปวดเกือบทุกวัน"
  จะให้ 4 หรือ 5 ก็เถียงได้ทั้งคู่ — ตรงนี้ต้องให้อาจารย์หมอหรือพยาบาลช่วยตัดสินเฉลย
